# Modes

Interactive mode applies when stdin and stdout are terminals, `--no-input` and `--json` both resolve off, as [Global flags](global-flags.md) resolves a flag and its variable, and `CI` is not set. Every other case is non-interactive mode, so machine output never waits for a human, as [D046](../decisions/D046-machine-output-never-asks.md) decides. Some agent tools run commands in a pseudo-terminal, so an agent sets `NCLY_NO_INPUT=1` in its environment.

| Situation | Interactive mode | Non-interactive mode |
|---|---|---|
| Every required value is given | Runs | Runs |
| A required value is missing | A form asks only for the missing values | Exit 2, `USAGE_INVALID`, and a hint with the full command |
| A step needs a confirmation and `--force` is absent | Asks for confirmation. Any answer but yes changes nothing and exits 2 with `CONFIRMATION_REQUIRED` | Exit 2, `CONFIRMATION_REQUIRED`, and a hint that adds `--force` |
| A step only a human can do, such as typing or granting a key | Asks | Exit 78, `TERMINAL_REQUIRED`, and a hint that names the command to run in a terminal |

The form for missing values asks before any other step, then the command runs as if the call had held those values. It asks for each required argument and each required flag that the call lacks, and, for a flag group whose `min` the call does not reach, which flag of the group to set, then that flag's value. A value whose declaration lists `values` is a choice among them. Any other value is a text field that suggests what [completion](completion-values.md) would suggest and accepts any other value, as completion does, and a variadic value asks for one value. Core asks for the missing values of an extension's command from its manifest, before it starts the extension, so every extension gets the form without code of its own. Ctrl-C at a form exits 130 with `INTERRUPTED` before the command does anything.

The form first checks the values that the call gave, so a value that its type rejects fails with `USAGE_INVALID` before the form asks anything. It then asks one value at a time, in the order of the usage line: each argument, each flag, then each group. A field's title is the argument's name, such as `name`, or the flag and its value, such as `--mood <word>`, and its description is the summary of that value. A group's choice lists each of its flags that the call did not set, with its value and its summary, and the chosen flag that takes a value asks for it next. An empty answer leaves its value missing, and the form's values pass the same checks as the call's, so either fails with `USAGE_INVALID` as a call without the form does. In non-interactive mode, and after a form that left a value missing, the hint shows the full command: the command as the `Next time:` line writes it, with each missing value in the notation of the usage line, such as `ncly hello pick <name> --mood <word> (--left | --right)`. The message names the first missing value. The hint does not run as is, so the answer holds no `next`.

After an interactive run that used this form, unless a signal stopped it, `ncly` prints on stderr, after the command's answer and its errors, the line `Next time:`, in bright black, then the equivalent command on its own line, indented by two spaces and without style: `ncly`, the command path, each argument, then each flag that the call set or the form filled, in the order of the declaration, each word quoted for a POSIX shell when it needs quotes. A switch shows as `--<name>`, or as `--<name>=false` when the call turned it off. When an argument starts with `-`, the arguments come last, after `--`. The global flags stay out of it. The command itself is never translated. The masked field of a key and a confirmation fill no missing value, so neither prints this line, and the line never holds a key or `--force`.

From [M07](../../milestones/M07-forms.md), these screens take the looks that Pascal picked, on stderr. A form uses Huh's Base16 theme: a thick bar at the left, in bright black, groups each field with its title, in cyan, its description and its suggestion, in bright black. In a choice, `>`, in yellow, marks the chosen value, which is green, while the other values keep the terminal's default color rather than Base16's white, which a light terminal cannot read. The key help under the form is bright black, with Huh's keys and the words of the SDK's catalog: `enter submit` under a text field, after `ctrl+e complete` when the field suggests values, and `↑ up • ↓ down • / filter • enter submit` under a choice. Without color, `>` alone marks the chosen value. The masked field of a key is a password field of the same form, which shows one `*` per typed character. A form leaves the screen once the human answers it. A confirmation is a prompt, never a button, as [D059](../decisions/D059-no-buttons.md) decides: `?`, in cyan, and the question, in bold, the facts that the answer rests on as labeled lines under it, indented by two spaces, with their labels in bright black and their values aligned, such as the new and the old path of a grant, then `[y/N]`, in bright black, on a line of its own under the facts, indented as they are, or at the end of the question's line when no fact follows. The human types the answer after `[y/N]`, and the question and the answer stay on screen.

A form and a confirmation leave the terminal as they found it, after an answer and after Ctrl-C. When `TERM` is `dumb`, the terminal cannot redraw a line, so a form asks each field on a line of its own, as Huh's accessible mode lays it out: its title, then the answer. The masked field turns echo off before its title shows, so it shows nothing as the human types, and drops what the human typed before its title. A choice lists its options by number under its title, then asks for the number of one, and an answer that names none of them, the end of input included, leaves its value missing.
