# Operations

The domain prepares an operation from resolved inputs and configuration, performs its steps, and verifies their results. Dry run uses that same preparation and reports pending checks, such as authentication. Execution repeats checks affected by changed inputs or destinations before applying effects. A dry run is not a reservation or a guarantee that the environment will stay unchanged.

Preparation checks the prerequisites that the invocation selects, such as a program or another extension, so a dry run fails with the code that execution would answer, and `pending_checks` holds only what execution alone can check, such as a key. A dry run is therefore the readiness check of one invocation, and [ncly doctor](../core-spec.md#ncly-doctor) the readiness check of the machine, as [D034](../decisions/D034-shared-preparation.md) decides. An agent needs no doctor call before each command.

Commands that incur a bill or can leave reusable partial work record an execution before the first such effect. The first are `ncly agent run` and transcript, and each uses one item and one paid step. Read-only discovery and dry runs create no run record. Each domain declares its recording support before code is written. Ordinary one-file tools do not acquire records or batch support merely by writing a file. The existing `resume` capability field stays false for these first commands; explicit continuation is in [COR-621](../../backlog/COR-621-resume-sdk.md#later).

The SDK's record support owns run IDs, durable records, step transitions, and result publication, for core and every Go extension. It persists each step's intent, which turns the step `unknown`, and its final status, in the order that [Records and evidence](records-and-evidence.md) requires, and derives [Retry safety](retry-safety.md) from the effects that the steps declare, so a domain never states retry safety a second time. The domain names its steps, declares the effect of each, verifies their results, and owns the evidence that makes them resumable. The program runner owns child processes, their environment, timeouts, and signals. It does not decide whether a business action is safe to repeat.
