# D017 Write acceptance criteria as testscript scenarios

Decided 2026-10-05. Each card names the testscript scenarios that prove it. End-to-end scenarios come before unit tests. M00 verifies the real parser, streams, modes, and shared outcome logic, including partial results. A later domain proves its effects, simulation, and recovery on its first real implementation. A recorded operation also proves its crash behavior with a boundary scenario, which kills it at every step boundary through a hook that lives only in the test binary, as [AGENTS.md](../../../AGENTS.md#work-on-a-card) asks.

**Why.** Pascal writes the specifications and agents write the Go. A scenario reads like a terminal session, so Pascal checks behavior without reading Go. Parser errors and misplaced output can make a command unusable by agents even when its success path works. Crash points picked by hand miss some, while the SDK's record support knows every step boundary, so one scenario shape covers each new step. [Asupersync](https://github.com/Dicklesworthstone/asupersync), a Rust async runtime, injects cancellation at its scheduling points and checks the same invariants after every run.

**Rejected.** A fault-injection variable in the release binary. Treating a contract fixture as proof that a future command avoids writes or duplicate paid requests. Stubbed services keep tests repeatable, but they do not prove that the real Python program and harness support the required protocol and restrictions.
