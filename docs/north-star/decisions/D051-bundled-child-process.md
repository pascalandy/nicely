# D051 Run a bundled extension as a child of the same ncly binary

Decided 2026-10-11. A Go extension exports one `extension.Extension` value from `sdk/extension`: its embedded manifest and catalogs, and its handlers. `extension.Main` runs it as `ncly-<domain>`. To bundle it, `cmd/ncly` passes the value to core in an explicit list, and core runs it by starting its own binary with `ncly-<domain>` as `argv[0]`, through the program runner, as busybox picks its applet from its name. [SDK](../contract.md#sdk) holds the rules.

**Why.** [D004](D004-minimal-core.md) bundles `skill` and could later let it leave the binary, and the contract promises that this needs no rewrite. As a child process, a bundled extension gets the arguments, environment, process group, cancellation, and answer check of an external one, with no second path to keep equal. Go's [context cancellation](https://pkg.go.dev/context#CancelFunc) only asks code to stop, so a handler running inside `ncly` that blocks on stdin would keep core from answering, while a child process ends at the SIGKILL of cleanup. The child costs one more start of `ncly` per call, a few milliseconds, and the archive still holds one binary. An explicit list in `cmd/ncly` shows every bundled extension in one place, while an `init` side effect would bundle a package merely because something imported it.

**Rejected.** Running the bundled handler inside the process of `ncly`, the first version of this decision, for the reason above, and because a shared process would forbid an extension `os.Exit`, the process environment, and its own signal handler. Bundling by `init` registration, as `database/sql` drivers do. Shipping each bundled extension as a separate executable in the archive, which [D004](D004-minimal-core.md) rejects.
