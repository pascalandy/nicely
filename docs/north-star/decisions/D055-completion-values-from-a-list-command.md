# D055 Complete an extension's values from a list command

Decided 2026-10-13. Completion gets the values that only an extension knows from the qualifying list command that an argument's or a flag's `values_from` names. [Completion values](../contract.md#completion-values) holds the rules.

**Why.** Only an extension knows values such as its skill names, and a list command already answers them for agents, so completion reuses that answer instead of a second path to the same data. A future value owned by another extension can come from that extension's list command, which composes through the CLI, as principle 12 asks. Core calling a command that an extension declares is no hook, as [D044](D044-additive-extensions.md) says, and it works for an extension in any language, because it needs nothing beyond the contract. Only a list command that declares effects that neither write user files nor bill qualifies, so a Tab never starts a write or a paid request, and core may kill it at the limit instead of waiting for its cleanup. A free network read still qualifies, because a list of remote items needs one. Core dispatches the list command itself, so the program that runs is the one whose declaration it checked, even when an installation changes the winning extension in between. The command still validates its own input, so a value that completion missed, such as a skill added a second ago, still works.

**Rejected.** Forwarding Cobra's `__complete` protocol to the extension, which every extension would have to implement, shell ones included, and which would make Cobra's protocol part of the wire contract. Static values in the manifest, which cannot list what the user configures or installs. A cache of values, which goes stale. A proxy list command in every consumer, which would repeat data that another extension owns. Starting `ncly <command> --json` again, whose second discovery could start another program than the one that core checked.
