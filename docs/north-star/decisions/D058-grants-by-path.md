# D058 Grant a key to an extension at its source, and let the extension answer what it lacks

Decided 2026-10-14, revised 2026-10-16 for M12. `ncly auth grant <service> <domain>` grants a key after a human confirms it in a terminal. `ncly auth revoke <service> <domain>` takes it back. A grant binds the service to the domain and source. Outside taps, the source remains the path where discovery found the extension, without resolving a link. A tap extension uses its canonical tap ID, independently of its publication path. An optional `tap` field extends the existing grants format, with no automatic conversion of path grants. Grants live in `grants.json` in the state folder. When core starts a command, it passes each granted key that the command declares. `NCLY_MISSING_KEYS` names the code of each declared key that core does not pass. Core never asks for a grant when it starts an extension. The extension answers `KEY_NOT_GRANTED` when this invocation needs the key, and its `next` is the grant command. A manifest marks an optional key in its `keys` table, as it marks a conditional program in `programs`. [Grants](../contract.md#grants) and [ncly auth](../core-spec.md#ncly-auth) hold the rules.

**Why.** Serious tools grant a secret to one consumer by an explicit command, and take it back the same way. A Docker service receives only the secrets that `docker service update --secret-add` gives it, and `--secret-rm` removes one. A Kubernetes pod receives only the secrets that its spec names, and `kubectl create rolebinding` grants a role to a subject. Nicely follows them with one command for each direction, with the service first, as `login` and `logout` take it.

The macOS keychain lets an app read an item without asking once a human chose "Always Allow", and it identifies the app by its code signature. Nicely's extensions carry no signature, and a hash of the executable would lose every grant at each update, which [D030](D030-trusted-extensions.md) wants to keep. The path where discovery found the extension stays the same across a Homebrew upgrade, because Homebrew updates the link in `bin/` and discovery never resolves it, while another `ncly-transcript` earlier in `PATH` has another path, so it inherits nothing.

Deno asks for a permission at the moment a program uses it, because the program runs inside Deno, which can pause it. Core cannot pause an extension, and before the start it cannot know whether this invocation needs the key, as a summary-only resume of transcript shows. A refusal by the extension with the grant command as its `next` keeps one prompt in one place. The variable `NCLY_MISSING_KEYS` lets the extension tell a missing grant from a missing key, because the absence of a key variable alone says neither, and it keeps the wire contract in the environment, as [D040](D040-wire-contract.md) asks.

M12 gives each tap a stable identity while updates select immutable publication paths. Grants follow that source across updates, as D030 requires. Another tap with the same domain receives no inherited grant. The retained `path` lets older readers remain conservative, as [Grants](../contract.md#grants) explains.

**Rejected.** A grant prompt when core starts an extension, which would ask for keys that the invocation may not need, and a prompt after the extension refused, which would start it again after it may have produced effects. A hash of the executable as its identity, and the target of its link, which every Homebrew upgrade changes. Granting from `ncly auth login`, because a key piped with `--stdin` has no terminal to confirm in. Grants in the local config, which would bring a config editor before taps need one. Passing `--force` to `grant`, which [D030](D030-trusted-extensions.md) rejects.
