# D054 Find the skills of installed extensions through ncly describe

Decided 2026-10-12. An extension ships a skill named after its domain, except the bundled `skill` extension, whose `nicely` skill teaches core and the skill domain. An external extension keeps it in the folder `ncly-<domain>.skill/`, beside its manifest and catalogs, and a Go extension embeds it in its `extension.Extension` value, whose installation writes that folder. `ncly describe` gives the folder in the entry of each extension's domain, and the `skill` extension reads it there, as any agent could. [M03](../../milestones/M03-describe.md) therefore comes before [M04](../../milestones/M04-skill.md). [Extensions](../contract.md#extensions) and [ncly skill](../../../extensions/skill/spec.md#ncly-skill) hold the rules.

**Why.** `skill` runs as a child of `ncly`, as [D051](D051-bundled-child-process.md) decides, and imports only `sdk/`, so the discovery code of the host in `internal/cli` is out of its reach. Through `ncly describe`, `skill` lists exactly the extensions that core runs, never one that core hides behind another, and the rule for where an extension's files sit stays in core alone. Naming the skill after the domain lets an agent go from a domain in `ncly describe` to `ncly skill view <domain>` without a lookup. A skill is a folder, because it can name files beside its `SKILL.md`, so it sits beside the manifest as the catalogs do.

**Rejected.** Moving discovery into `sdk/`, because it belongs to the host, and a second caller would freeze its internals as a public API. Passing the list of extensions to `skill` in a variable, which adds to the environment of every extension a fact that only one needs. Searching `PATH` again inside `skill`, a second implementation that could pick another extension than core does. One `SKILL.md` file beside the manifest, which could not hold the files that a skill names.
