# D050 Check an extension's answer before the caller sees it

Decided 2026-10-10. With `--json`, core holds the extension's stdout until the extension exits, forwards its stderr except the last line, and passes the answer on only when it follows [Output](../contract.md#output) and [Exit codes](../contract.md#exit-codes). Otherwise it answers `RUNTIME` with exit 1. Without `--json`, the extension writes to the streams of `ncly` directly, and core checks its exit code. The set of error codes is open: a caller acts on the exit code of a code that it does not know. [Answer check](../contract.md#answer-check) and [Error codes](../contract.md#error-codes) hold the rules.

**Why.** A caller reads stdout on success and the end of stderr on failure, so a broken answer must be stopped before it reaches either: checking a copy would leave the caller holding it. Human output needs the real terminal for its styles and forms, and a person reads it, so passing it through costs no safety. A report keeps its answer on stdout even when it fails, and a text command ignores `--json`, as Output allows, so the manifest names each command's kind of result and core checks each kind by its own rule. Core's codes grow with the milestones and every extension adds its own, so a closed set would turn a valid code from a newer extension into a failure. The exit code already tells a caller what to do, so an unknown code needs no more.

**Rejected.** Passing the answer through and checking a copy, for the reason above. A code of its own for a protocol failure, because a caller does what `RUNTIME` asks: never rerun automatically, and inspect. Rejecting a core code that this version of `ncly` does not know, because an extension built for a later release may use it.
