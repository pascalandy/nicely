# D048 Describe an extension in a manifest and catalogs beside it

Decided 2026-10-10. An external extension is three things side by side: its executable `ncly-<domain>`, its manifest `ncly-<domain>.toml`, and its catalogs in `ncly-<domain>.locales/`. The manifest holds the same command declarations as core's commands, with catalog IDs instead of text, and the extension's own error codes with their exit codes. Core reads them without starting the extension, so help, completion, validation, and discovery treat every command alike. [Extensions](../contract.md#extensions) holds the schema.

**Why.** Help and completion never start an extension, so its text has to be on disk. Catalog IDs keep every string translatable, with a description for the translator, as principle 7 requires, and an extension's catalogs then follow the same format and the same parity test as core's. The catalog files list the languages that an extension speaks, so the manifest needs no list that could disagree with them. Browser extensions keep the translated strings of their manifest in [`_locales/<lang>/messages.json`](https://developer.chrome.com/docs/extensions/reference/api/i18n), each with a description, beside the manifest in the same way. Declared codes let core check that an answer's exit code matches its leading code, and their order decides which one leads.

**Rejected.** English text inside the manifest, because it would bypass the catalogs. Catalog tables inside the manifest, because a translator would then edit the file that declares the commands, and an extension's catalogs would differ from core's. Running the extension to learn its help, as Docker asks its CLI plugins for their metadata, because help would then depend on a program that may hang. A `languages` key, as [#8](https://github.com/pascalandy/nicely/issues/8) proposed, because the catalog files already list the languages.
